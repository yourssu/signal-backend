# 경량 SDD 워크플로

## 1. Issue

Git 공유 파일 변경 전에 GitHub Issue를 확인하거나 생성한다. Issue가 요구사항 원본이며 구현은 별도 브랜치 또는 worktree에서 진행한다.

## 2. 분류

파일 수보다 위험도를 우선한다.

- Small: 1~3개 파일, 단일 원인, API·DB·보안·배포 변경 없음
- Medium: 4~10개 파일 또는 여러 계층, API 계약·도메인 규칙·외부 연동 변경
- Large: DB 스키마·인증·결제·배포·다중 저장소 또는 독립 작업 2개 이상

한 파일이어도 DB·인증·결제·배포를 바꾸면 Large다. 분류와 근거를 사용자에게 알리고 사용자가 등급을 바꿀 수 있게 한다.

## 3. 산출물

- Small: 채팅의 짧은 계획만 사용한다.
- Medium: `.agents/local/specs/issue-<번호>/spec.md`, `plan.md`를 작성한다.
- Large: Medium 산출물에 `tasks.md`를 추가하고 의존성과 병렬 wave를 표시한다.

스펙은 장문 회의록이 아니다. GitHub Issue를 공용 요구사항 원본으로 사용하고, 로컬 spec에는 구현 판단에 필요한 확정 내용만 기록한다. spec·plan·tasks는 Git에 커밋하지 않으며 각 worktree에서 Issue를 바탕으로 생성한다.

## 4. 구현

- 독립 작업만 병렬화한다.
- 각 구현자는 격리된 worktree와 한정된 파일 범위를 사용한다.
- 구현자는 다른 구현자의 파일을 임의로 수정하지 않는다.
- 요청 범위 밖 개선은 기록만 하고 현재 PR에 포함하지 않는다.

## 5. 리뷰

- Small: 구현자가 diff와 검증 결과를 확인한다.
- Medium: 구현 컨텍스트를 받지 않은 리뷰어 1명이 Issue·스펙·diff·검증 증거를 검토한다.
- Large: 코드·회귀 리뷰와 보안·운영 리뷰를 병렬 수행한다.
- P1·P2 발견은 수정 후 재검토한다. 스타일 선호와 범위 밖 리팩토링은 차단 사유가 아니다.

## 6. 검증과 전달

`.agents/hooks/verify-before-pr.sh`를 실행하고 API·브라우저처럼 자동화되지 않은 필수 검증을 실제 수행한다. 실패하거나 실행하지 못한 필수 검증이 있으면 PR을 만들지 않는다.

에이전트는 `.agents/hooks/create-pr.sh`로 검증·push·PR 생성까지만 수행한다. PR merge와 auto-merge는 사용자만 수행한다.
